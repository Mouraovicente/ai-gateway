# Local benchmark: gateway overhead vs. backend (2026-09-20)

Goal: how many req/s does `ai-gateway` itself sustain, separately from whatever LLM backend it's calling, and what's the latency floor. Everything here is local, single instance, Windows, LocalStack (not real AWS) — read it as "where's the ceiling," not as a production capacity number.

## Method

- `bench/stubollama` replaces Ollama with a tiny Go HTTP server that answers `/api/chat` (native Ollama shape: `message.content`, `done`, `prompt_eval_count`, `eval_count`, NDJSON when `stream:true`) with a fixed artificial delay (`-latency`, default 0) and a configurable number of stream chunks (`-tokens`). This isolates gateway overhead from real model inference time.
- Load generated with [`hey`](https://github.com/rakyll/hey) (`go install github.com/rakyll/hey@latest`).
- A throwaway tenant (`bench-key`, tenant `tenant-bench`, tier `free`, `rpm_limit=100000`, `monthly_token_budget=1e9`) was seeded into the LocalStack `tenants` table via `bench/seedbench/main.go`, using the same SHA-256 hash scheme as `internal/auth.HashAPIKey`. `bench-key` is an obviously fake dev-only key; it is not used anywhere else and can be deleted from the local `tenants` table without affecting other tests (re-seeding is one `go run` away).
- Every scenario: gateway on `:18090`, body `{"model":"nuva/fast","messages":[{"role":"user","content":"ping"}],"max_tokens":8}`, header `Authorization: Bearer bench-key`, 30s window (20s for the real-Ollama reference, since it's slow and CPU-bound), no separate warm-up discard — `hey`'s own histogram already averages out first-request DNS/dial noise, and at this RPS a 5s warm-up would throw away a large fraction of an already-small sample.
- Full reproduction: `bench/run.sh` (builds the stub and gateway, seeds `bench-key`, runs all scenarios in sequence, prints a summary per run).

## Hardware

- CPU: Intel Core i7-11800H @ 2.30GHz, 8 cores / 16 threads
- RAM: 15.7 GiB
- OS: Windows 11, Git Bash
- Docker Desktop running LocalStack 3.8.1 (DynamoDB + SQS only) alongside otel-collector, Grafana, Prometheus, Tempo containers — i.e. the box was not idle during the run.

### What changed, and why the numbers moved

| Before | After |
|---|---|
| ~11 store round trips inline per request (1 auth GetItem, 1 reserve UpdateItem, 1 request PutItem, ~8 trace-event PutItems, 1 settle UpdateItem, 1 SQS SendMessage) | 2 inline (auth GetItem, reserve/settle UpdateItem); the request row and all trace events go to a bounded queue and leave as **one** BatchWriteItem of up to 25 items; the usage event goes to its own queue |
| An SQS publish sat in every request's deferred cleanup | Async worker, 3s per message, drops and counts instead of blocking |
| No way to measure the gateway without the emulator | `STORE_BACKEND=memory` |

The remaining LocalStack ceiling (~19 req/s) is still the emulator: the two DynamoDB calls that must stay synchronous (auth and budget, both correctness-critical) are what is left, and they are ~10x faster against real DynamoDB than against a SQLite-backed single process on a busy dev box.

## Interpretation of the original run: where was the ceiling?

**It's not the gateway's own code path, and it's not the backend — it's LocalStack.** Three findings pin this down:

1. **RPS is flat at ~7/s from concurrency 10 through 100**, whether the stub backend answers instantly (scenario A) or with an artificial 200ms delay (scenario B). If the gateway's HTTP handling, JSON marshaling, or routing logic were the limit, adding concurrency would still move the needle, and a slower backend would show up as *higher* per-request latency without capping throughput this hard. Neither happens — throughput pins at the same number regardless of backend speed or client concurrency, which is the signature of a single shared, serialized resource downstream.
2. **The auth-reject path (scenario E) sustains ~65 RPS** — 9x the full pipeline's throughput. That path does one DynamoDB `GetItem` (`ResolveAPIKey`) and stops; it skips `budget.Reserve`, the backend call, `budget.Settle`, the trace writes, and the SQS usage publish. Every one of those extra steps is a DynamoDB round trip or an SQS publish against LocalStack, and cutting them out is what buys the 9x.
3. **`docker stats` showed the LocalStack container at ~68% CPU sitting at idle** (a snapshot taken between runs, not mid-load), on a container capped well below the host's 16 logical cores. Under load its single-process DynamoDB emulator (backed by SQLite, not a real distributed store) becomes the serialization point every request queues behind.

Per successful request the gateway does, at minimum: 1 DynamoDB `GetItem` (auth), 1 DynamoDB conditional `UpdateItem` (budget reserve), 1 DynamoDB `PutItem`-or-similar for the request trace + N for trace events, 1 DynamoDB `UpdateItem` (budget settle), and 1 SQS `SendMessage` (usage event) — five-plus round trips to a single-process local emulator, per request. At ~7 RPS that's 35+ LocalStack operations/sec, which lines up with where a SQLite-backed emulator on a shared dev box plateaus.

**Scenario D (real Ollama)** is, unsurprisingly, capped by the model itself — 0.5–2 RPS on CPU inference of `qwen2.5-coder:1.5b`, well under even the LocalStack ceiling. In a deployment where DynamoDB is the real AWS service (not LocalStack) and the backend is a real hosted LLM, the ceiling moves: real DynamoDB comfortably does thousands of ops/sec, so the practical ceiling becomes whichever is slower between the LLM backend and the gateway's own per-request work — which this benchmark could not isolate cleanly, because LocalStack got in the way first. **That's the main actionable finding: this benchmark, as run, measures LocalStack's throughput, not the gateway's.** To actually isolate gateway-only overhead, the DynamoDB/SQS calls need to be swapped for in-memory fakes (or the test run against real (non-free-tier) AWS resources) so the pipeline's own CPU/allocation cost per request is what's left standing.

## Caveats

- **Ephemeral-port exhaustion is the memory-mode benchmark's own ceiling, not the gateway's.** At 15k req/s on Windows, the full `bench/run.sh memory` sequence burns through the ephemeral port range in the first scenarios; later scenarios in the same run then show timeouts that have nothing to do with the server (scenario E measured 6 req/s inside the sequence and 62,739 req/s when run on its own after a TIME_WAIT cooldown). The memory-mode table above uses the isolated runs. Anything above ~10k req/s on this box should be read as "the load generator and the OS gave up first".
- **The pre-auth per-IP limiter is disabled for these runs.** `bench/run.sh` sets `IP_AUTH_FAILURES_PER_MINUTE=1e8` before every scenario, including E (auth reject). At the real default (60/min) the load generator's hundreds of 401s per second would trip the limiter within the first second and every subsequent request would be a 429 from the pre-auth path instead of a 401 from `ResolveAPIKey` — measuring the limiter's rejection cost instead of the auth path's. Disabling it isolates the number this report actually wants.

- Windows dev box, not Linux/production hardware; absolute numbers won't transfer.
- LocalStack is not AWS — its DynamoDB/SQS emulation has very different (worse, single-process) scaling characteristics than the real services, and this benchmark shows that gap dominates the result.
- Single gateway instance, no load balancer, no `-race` build (a race build would be slower and is irrelevant to a throughput number).
- `hey`'s default per-request client timeout truncated the 200-concurrency runs (A/200, B/200) before they reached steady state — they show saturation collapse, not a stable rate.
- No warm-up discard was applied; given the achieved RPS (single digits), 30s already yields a small sample (~30–250 requests per scenario), and a 5s warm-up would have thrown away 15-30% of it for negligible noise reduction.
- Scenario D's Ollama model is CPU-bound and slow by design (a small local model for cheap dev iteration); it is not representative of a production hosted LLM's latency.

## Reproduce

```bash
go install github.com/rakyll/hey@latest   # if not already on PATH
export AWS_ACCESS_KEY_ID=test AWS_SECRET_ACCESS_KEY=test AWS_REGION=us-east-1 AWS_ENDPOINT_URL=http://localhost:4566
bash bench/run.sh
```

`bench/run.sh` builds `bench/stubollama` and `cmd/gateway`, seeds the `bench-key` tenant, and runs scenarios A, E, C, B, then D (against real Ollama) in sequence, killing every process it started on exit.

For the gateway-only numbers, run it in memory mode — no LocalStack, no AWS, tenants (including `bench-key`) from `config/tenants.dev.yaml`:

```bash
bash bench/run.sh memory
```

At these rates the OS runs out of ephemeral ports before the gateway runs out of headroom; re-run any single scenario on its own, after a TIME_WAIT cooldown, before believing a low number from late in the sequence.
